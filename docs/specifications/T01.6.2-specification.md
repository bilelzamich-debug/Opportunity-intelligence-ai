## 5. Architectural constraints binding the implementation

1. **C1 — Outside the object model.** No Intelligence Object type may be
   imported, held, produced or referenced. (AC2, Art. V, CI-1, N-10 precedent.)
2. **C2 — Metadata only, never content.** Only identifiers, engine, time,
   configuration reference and outcome. No object payload, no claim text, no
   confidence, no explanation. (AC3, IOM §2.5, §4.6.)
3. **C3 — Never in lineage.** `participates_in_lineage` is permanently `False`;
   attempts to use a processing record as lineage, as Evidence, or as a
   confidence contribution are refused. (Art. IV, Art. V, CI-1, N-10.)
4. **C4 — Orchestration owns no storage.** The store is **supplied** to the
   `Orchestrator`, never constructed by it — the same rule already applied to
   `failure_store` at T01.6.1. (PKP v2 §4.12.)
5. **C5 — Sequences, never judges.** The store records and reports. It takes no
   scheduling action, skips nothing and retries nothing. (AD-04, M-36 open.)
6. **C6 — Per cycle.** Every processing record carries its `cycle_id`. (N-17.)
7. **C7 — Reproducibility.** Every record carries the
   `engine_configuration_ref` in force. (N-4.)
8. **C8 — Empty ≠ failed.** The outcome is retained verbatim and never
   collapsed into a boolean. (N-10.)
9. **C9 — Immutable, append-only.** Infrastructure state is immutable (N-7,
   N-10 rationale: "both are immutable"). Reprocessing appends; it never
   overwrites. History is what makes reprocessing detectable.
10. **C10 — Thread-safe.** N-11 permits concurrent stages 1–2.
11. **C11 — NOT_ATTEMPTED is not processing.** An item the cycle never reached
    was not processed; recording it would mask starvation, a named failure mode
    (PKP v2 §4.12), and would corrupt idempotence.

## 6. Placement

No decision record names a home for processing state. Two candidates:

- `oip/configuration.py`, beside `ConfigurationStore` and `FailureStore`,
  following N-10's rationale that "one state surface with a clear boundary is
  preferable to two".
- `oip/orchestration.py`, as orchestration state.

**B-12 decides it.** Option 4 — "Failure records in the same store as
orchestration state" — was rejected in favour of co-locating failure records
with configuration. The architecture therefore treats *orchestration state* as
a surface **distinct from** the failure store. Placing processing state in
`configuration.py` would re-merge exactly what B-12 kept apart.

**Resolution: `oip/orchestration.py`.** This also avoids an import cycle:
`InvocationOutcome` is defined there, and inventing a parallel outcome enum
elsewhere would breach the no-new-vocabulary rule. Ownership is preserved by C4
— the class lives in the control module but every instance is supplied by the
caller.

## 7. Unresolved ambiguities — surfaced, NOT resolved here

| # | Ambiguity | Fail-closed treatment |
|---|---|---|
| **A1** | Does a change of `engine_configuration_ref` (N-4) make an already-processed input eligible for reprocessing? No decision record states this. | `engine_configuration_ref` is **recorded on every record** and queryable. The store expresses no opinion. `has_processed` keys strictly on the ratified pair (engine, input). |
| **A2** | Does a **FAILED** attempt count as "processed" for scheduling? N-10 says Orchestration reads failures "for scheduling and idempotence" but states no rule. M-36 open. | The outcome is recorded and distinguishable (C8). `has_processed` means "an attempt is recorded", stated explicitly in the docstring. No retry decision is made or implied. |
| **A3** | What should happen when reprocessing is detected? | Nothing. The acceptance criterion says "detectable". Suppression is scheduling policy under M-01/M-36, both open. |
| **A4** | Is the unit of processing the work **item** or each **input**? Not ratified. | One record per invocation carrying the full `input_ids` tuple (faithful to what happened), indexed per input id. Both readings are answerable from the recorded facts; neither is privileged by the store. |
| **A5** | Retention of processing state. | None specified. Append-only and unbounded, matching the gap N-10 already records for failure records. |
| **A6** | Should `produced_ids` be retained? | Retained: they are identifiers, hence metadata under C2, and `InvocationRecord` already carries them. No content accompanies them. |
