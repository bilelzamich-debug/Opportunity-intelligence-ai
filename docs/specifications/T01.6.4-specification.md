## 3. Dependencies honoured

- **T01.6.1** — `Orchestrator` already serialises *whole cycles* under a lock (`CycleStateError` if a cycle is already running). That is cycle-level, **not** the stage-level boundary N-11 requires. Preserved unchanged.
- **T01.6.2** — `ProcessingStateStore`, thread-safe, append-only.
- **T01.6.3** — `FailureSurface`, `FailureRecord` attribution, store-fault containment. Concurrency must not weaken any of it.

## 5. Architectural constraints

1. **C1 — Stage 1–2 concurrent; stages 3–9 serialised.** Exactly the N-11 table. No other partition.
2. **C2 — The batch is the stability boundary.** Interpretation is serialised *"one batch at a time"* (N-17).
3. **C3 — Version branching impossible**, following from C1 + single create authority (R-1).
4. **C4 — Concurrency changes no semantics.** Acceptance, lineage, integrity, confidence and object semantics are untouched. This layer moves work only.
5. **C5 — Orchestration owns no storage** and performs no knowledge judgement (AD-04, v2 §4.12).
6. **C6 — No deadlock, no starvation, no duplicate invocation** (named failure modes).
7. **C7 — Failure semantics preserved** under concurrency: N-10 record/continue/surface, never masked.
8. **C8 — Bounds still enforced** (N-17): work-set size and wall-clock budget.
9. **C9 — Backward compatible.** Existing sequential `run_cycle` behaviour unchanged by default.
10. **C10 — Surfaces stay separate** (B-12): orchestration, processing, failure, Intelligence Objects.
11. **C11 — No invented concurrency limit** (M-56 open).

## 7. Unresolved ambiguities — surfaced, NOT resolved

| # | Ambiguity | Fail-closed treatment |
|---|---|---|
| **A1** | "Preserve deterministic behaviour" vs. N-4, which guarantees only reproducible *inputs*. | Concurrency is made deterministic in every respect the platform controls: **the recorded invocation order is always work-set order**, regardless of completion order; bounds are applied deterministically; results are reassembled by index. Engine *outputs* remain non-deterministic per N-4 — that is ratified and unchanged. |
| **A2** | How many workers for concurrent stages? | **Not specified anywhere; M-56 open.** Caller-supplied `max_workers`, default **1** (sequential — byte-identical to today's behaviour). No CPU-count or cost-derived default. |
| **A3** | May stage 1 and stage 2 run concurrently *with each other*, or only within a stage? | N-11 groups them in one row — "1 Evidence, 2 Facts — Concurrent" — with the reason "operations are independent per source". Both are in the concurrent class; the decision draws its line **between stage 2 and stage 3**, so items in stages 1–2 are mutually concurrent. Nothing narrower is stated. |
| **A4** | Must a serialised item wait for in-flight concurrent items? | Yes, by direct implication: interpretation must see a *stable* population, which is impossible while acquisition is still writing. The boundary is a **barrier**. This is the plain reading of "one batch at a time" plus "stable population", not an invention. |
| **A5** | Queue bounds for upstream backlog. | **Not specified.** Not built. Surfaced. |
| **A6** | Does concurrency apply *across* cycles? | No — N-17 serialises cycles and T01.6.1 enforces it. Concurrency is **within** a cycle only. |
| **A7** | Stage 8 has no engine (C-02). | Classified by object type as serialised. No engine invented. A stage-8 item can only be expressed via `produces=EXECUTION_RECORD`. |

## 9. Implementation plan

Smallest architecture-compliant change; all additive.

**Step 1 — `oip/enums.py`: stage classification.**
`ENGINE_STAGE` (8 entries, Orchestration absent — it owns no stage) and `CONCURRENT_STAGES = frozenset({1, 2})` derived from N-11's table. No new enum type.

**Step 2 — `oip/orchestration.py`: `ConcurrencyClass`.**
Two members, `CONCURRENT` and `SERIALISED`, exactly N-11's two classes. `WorkItem.concurrency_class` resolves via `produces` (object type → stage) else engine, failing closed for Orchestration and for any unclassifiable item.

**Step 3 — `WorkSet.concurrency_plan()`.**
Partitions the work set into ordered **phases** preserving caller order: maximal runs of concurrent items become one parallel phase; each serialised item is its own phase. This is the barrier of A4.

**Step 4 — `Orchestrator(max_workers=1)`.**
Default 1 ⇒ current sequential path unchanged. Above 1, concurrent phases dispatch via a thread pool while serialised items run one at a time on the calling thread. **Invocation records are reassembled in work-set order**, so the recorded history is identical whatever the completion order (A1). Bounds, failure recording, processing state and cycle serialisation all unchanged.

**Step 5 — `ConcurrencyBoundary`** — a read-only verifier proving AC1–AC3 mechanically from a `CycleRecord`: serialised stages never overlap in time; concurrent items never interleave with a serialised item; at most one writer per object type at any instant (version branching impossible).

**Explicitly NOT built:** queue bounds (unspecified), concurrency limits derived from cost (M-56), graph partitioning (OQ-14), retry (M-36), cross-cycle concurrency (N-17), any change to acceptance/lineage/confidence.
