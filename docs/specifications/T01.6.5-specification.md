## 5. What "inputs exist" means — derived, not invented

v2 §4.12 states Orchestration's input is *"the existence and status of objects awaiting processing"* and its dependency is the *"Knowledge Store (to determine state)"*. §5.5 grants *"Read state only"*. IOM §2.5 limits this to *"status metadata only, never content"*.

So the guard answers exactly one question per work item:

> **Do the declared `input_ids` exist in the Store, and are they of the type this engine consumes (N-14)?**

Both halves are ratified: existence from §4.12, the type mapping from N-14's table.

**Research is the sole exception.** N-14 gives it no direct input (Evidence is the root, `derives_from` empty per E-V1), so a Research item requires no inputs. This is ratified, not inferred.

## 6. Architectural constraints

1. **C1 — Reject, never reorder.** Silent reordering would violate N-17's directive model and AD-04.
2. **C2 — Never infer or insert work.** No implicit items; no stage synthesis.
3. **C3 — Metadata only.** Existence, type, status. Never content.
4. **C4 — Store is read-only** here, and Orchestration owns no storage: the resolver is *supplied*.
5. **C5 — Read the Store, not the graph** (N-6 lag).
6. **C6 — No knowledge judgement.** Type identity is structural, not semantic.
7. **C7 — Preserve N-11/N-17** exactly: phase plan, barrier, bounds, cycle serialisation.
8. **C8 — Deterministic**: rejection depends only on the work set and store state.
9. **C9 — Backward compatible**: no resolver supplied ⇒ behaviour identical to today.
10. **C10 — Surfaces stay separate**; a rejection is not an engine failure (N-10) and must not be recorded as one.
11. **C11 — Fail closed** on anything unclassifiable.

## 8. Document conflicts

**None.** v2 §4.12, §4.13, §5.5, IOM §2.5/§2.6, N-14, N-17, N-18 and N-6 agree on every binding point.

One **apparent** tension, resolved: N-17 says Orchestration is *"directive, not reactive"* and *"does not react to object availability"*. That governs **what work is planned** — the caller plans. This task **rejects invalid work**, which is v2 §4.12's explicit *"enforce stage ordering"* responsibility. Checking a declared input exists is validation of a given plan, not selection of work. The two are complementary, which is why N-17 itself binds T01.6.5.

## 9. Implementation plan

Smallest architecture-compliant change; all additive.

**Step 1 — `oip/enums.py`: `ENGINE_INPUT_TYPE`.** N-14's direct-input column, 7 entries. `RESEARCH` absent (no input, E-V1 root); `ORCHESTRATION` absent (consumes nothing).

**Step 2 — `oip/orchestration.py`: `SequencingError`, `SequencingViolation`.** Rejection is distinct from engine failure (N-10).

**Step 3 — `StateResolver` Protocol + `SequencingGuard`.** Supplied, not constructed (C4). Resolves `object_id → ObjectType | None` and status, reading the Store only. Checks per item: Research needs no inputs; every other engine needs each declared input to exist and to be of its N-14 type. Produces `SequencingCheck` (frozen, itemised reasons).

**Step 4 — `Orchestrator(state_resolver=None)`.** Default `None` ⇒ unchanged. When supplied, each item is checked **immediately before invocation**, inside the existing phase/barrier machinery. A rejected item is recorded `REJECTED_OUT_OF_ORDER` — **not** `FAILED` (no engine ran; N-10's empty/failed distinction must not be muddied) and **not** `NOT_ATTEMPTED` (that means bound-reached; T01.6.2 refuses it as processing). The cycle **continues** (N-17/N-10 shape).

**Step 5 — `WorkSet.sequencing_report(resolver)`** — pre-flight, read-only, mutates nothing.

**Explicitly NOT built:** stage-skip prohibition (OQ-10, P6); backflow rules (OQ-11, P7); reordering (C1); implicit items (C2); status preconditions (A1); retry/skip (M-36); anything touching acceptance, lineage, confidence, lifecycle or ownership.
