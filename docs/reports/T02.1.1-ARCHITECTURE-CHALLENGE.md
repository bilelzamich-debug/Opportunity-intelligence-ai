## 4. Hidden implications — three findings that STRENGTHEN the blocker

These were missed previously and were the challenge's best hope of a false
positive. Each turned out to confirm the gap.

**4.1 N-03 (RATIFIED) depends on the missing taxonomy.**
N-03 §"Family 1" makes **"source-type coverage"** a stage-1 Evidence proxy
measure and a phase exit criterion. A ratified success measure is therefore
*already* resting on a vocabulary that does not exist. N-03 enumerates no types.

**4.2 T02.3.1 (P2 exit) requires "Evidence acquired from every defined source
type."** The phase gate is unsatisfiable while the set of "defined" types is
empty — confirming the backlog itself assumes M-16 closes first.

**4.3 N-16 anticipates the gap explicitly.** Its *Revisit Conditions*:
> "if Pattern Intelligence needs type-level diversity at acceptance rather than
> on demand, which would justify promoting a small **type-vector** into Tier 1."

A ratified decision contemplating a future type-vector is direct evidence that
types are **not** currently an enumerated set.

**4.4 `tags` cannot substitute.** IOM line 281: `tags` "must never carry
meaning any engine depends on — that would constitute a private channel and
breach Principle 4." Using `tags` as an informal taxonomy is explicitly
forbidden.

**4.5 S-05 stratifies by source type** ("sample rate rises for source types
showing elevated drift") — a fourth ratified dependency on the absent
vocabulary. It enumerates none.

## 6. Challenging my own previous investigation

Assuming my earlier reports contained mistakes, I found **two genuine errors** —
both of which made my earlier reports *weaker* than the evidence warrants:

**Error 1 — I under-stated the blast radius.** My proposal (§1.6) claimed S-02
and N-16 were the ratified decisions resting on M-16. **Wrong: there are four.**
N-03 (source-type coverage as an exit criterion) and S-05 (sampling stratified
by source type) also depend on it. M-16 is load-bearing for more ratified
material than I reported.

**Error 2 — I mis-stated one AC2 justification.** I wrote that the trust range
[0.0, 1.0] is "inherited from the ratified Evidence contract." Precisely: that
range is enforced in **`oip/evidence.py`**, a **P1 implementation artefact**,
and the IOM annotates the attribute "(OPEN QUESTION-28)" without stating a
range. H6 confirms **zero** ratified statements give trust a numeric range. The
range is therefore an implementation convention inherited from prior code, not
a ratified fact. It remains defensible for *storage* (it changes no behaviour
and matches the existing field), but my earlier wording overstated its
authority.

## 7. Proof that no deterministic implementation exists

For AC1 a conforming implementation must answer: *given a source, which member
of the closed taxonomy is its `source_type`?*

1. The answer's range is the taxonomy's member set (backlog AC1: "closed
   taxonomy").
2. That set is defined nowhere (H1, H2, H4, H5).
3. One candidate literal exists, and it is illustrative (H3).
4. It cannot be derived from `acquisition_method`, `access_conditions` or
   `capture_fidelity` — each is free text with a single example value.
5. It cannot be borrowed from `tags` (IOM line 281 forbids load-bearing tags),
   nor from independence grouping (type-free by N-16/S-04).
6. No engine is authorised to assign it (H8).

A function whose range is undefined and whose authority is unassigned is not
determinable. Any implementation must **choose** the member set — which is an
architectural decision (F2) that would close M-16 by implementation (F3).

The same argument holds for AC3 by IOM §3.9's "blocking" designation and M-43.

**Therefore no deterministic implementation exists without a new ratified
decision.** ∎
