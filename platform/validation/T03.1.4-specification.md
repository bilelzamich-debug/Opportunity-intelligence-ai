## 3. The design

### 3.1 What already exists (assembled, not rebuilt)

`fact.py` (untouched): `Fact.with_attachment` (new version, lineage
extension, duplicate-refusal, justification correspondence, N-16 count
math), `MergeJustification` (EQUIVALENT-only, reason mandatory),
`FactRegistry.find_equivalent/assess_all`, F-I2 integrity verification.
`claim.py` (untouched): `MERGE_POLICY`, `assess_equivalence`.
`store.py` (untouched): `write_fact(fact, predecessor_id)` with V11,
`transition`, `allocator.succeed`, I5 single-ACTIVE enforcement.

### 3.2 The merge flow in `extract()` (pre-write interception)

After decomposition, BEFORE any `write_fact`:

1. `existing = store.facts.find_equivalent(claim)` — the only verdict
   that merges is EQUIVALENT (S-3). No equivalent ACTIVE Fact → the
   separate path (3.4).
2. **Replay refusal**: if the canonical already attaches THIS Evidence,
   the extraction is a replay → recorded `MERGE_FAILED` /
   `EVIDENCE_ALREADY_ATTACHED` refusal; no second attachment is
   fabricated (F-I2/`with_attachment` refuses it anyway — the refusal
   is recorded rather than leaked as a raw exception).
3. `MergeJustification(verdict=EQUIVALENT, reason=assessment.reason,
   merged_evidence_ref=request.evidence_ref, merged_at=now)` — F-I4;
   the reason IS the S-3 four-condition statement.
4. `identity = store.allocator.succeed(canonical.attributes.identity)`
   (new object_id, version = predecessor+1, V11/R-1).
5. `merged = canonical.with_attachment(attachment, justification,
   identity=identity)` — F-I2 machinery.
6. **V5-safe confidence re-derivation**: support = min over the
   effective_confidence of EVERY Evidence in the widened upstream set
   (all attachments' evidences, old and new); assertion =
   min(predecessor's assertion_confidence, this extraction's
   extraction_confidence); `Confidence.create(support, assertion,
   upstream_ceiling=support)`. The predecessor ceiling is never
   inherited blindly: a weaker corroborating source lowers the
   canonical's support, exactly as V5 demands.
7. Explanation states the merge, the justification and the ceiling
   re-derivation.
8. `store.transition(canonical, SUPERSEDED, "corroborated: equivalent
   extraction attached [D-05, F-I4]")` — BEFORE the write, because I5
   refuses a second ACTIVE version of one lineage.
   **REVISED DURING BUILD (T03.1.4, recorded):** the originally
   specified restore-on-failure is IMPOSSIBLE — `SUPERSEDED` is a
   TERMINAL state under R-2 (`oip/enums.py` `_TERMINAL_STATES`), so
   `transition(→ACTIVE)` after supersession is refused by
   `with_status`. The implemented contract instead closes the failure
   surface STRUCTURALLY: V5 cannot fail (the ceiling is re-derived as
   the min over the widened upstream set — the merged version's
   effective confidence IS its ceiling), V11 is allocator-consistent
   (`succeed()`), V12 carries no DUPLICATES on the merge path, and
   Evidence references cannot introduce a lineage cycle; the
   fact-payload acceptance rules are pre-satisfied (F-V1 trivially,
   F-V2 by the extraction gates, F-V3 by `decompose()`, F-V4 by
   request validation, F-V5 by `with_attachment`'s count invariant,
   F-V6 unwired by default [T03.2.1]). Should a write still fail
   (defensive path, exercised by a stubbed test), the refusal is
   recorded naming the exact surviving state: the canonical is
   SUPERSEDED with every attachment intact and no successor — data
   intact, fully auditable, nothing silent [N-10]. `try_write` was
   evaluated as a pre-write dry run and REJECTED: it skips the
   fact-payload rules (no `fact=` argument) and requires
   `oip.lineage.Lineage`, a 7th oip import that would break the
   dependency budget.
9. `store.write_fact(merged, predecessor_id=canonical.object_id)`.
10. Registry-gap check, anchor registration (T03.1.3 invariant: only
    accepted extractions register), equivalence report (predecessor
    auto-excluded: SUPERSEDED facts are not in `active_facts`).
11. Concurrent-merge races — **DECISION (T03.1.4, recorded):** the
    allocator's `BranchingError` is undistinguished from other
    transition refusals; fabricating a dedicated `CONCURRENT_MERGE`
    reason would assert a concurrency diagnosis the store does not
    make. Races surface as `MERGE_FAILED` / `MERGE_NOT_POSSIBLE`
    (detail names the allocator error) — the conservative under-merge
    outcome; a re-run then merges into the new canonical.
    `CONCURRENT_MERGE` remains in the closed reason set as reserved,
    unemitted.

### 3.3 The separate path (no EQUIVALENT match)

`duplicates_targets` = every ACTIVE Fact whose verdict against the new
claim requires it (`CONTAINMENT` or `UNCERTAIN`, i.e. `MERGE_POLICY`'s
`SEPARATE_WITH_DUPLICATES`), recorded on the NEW Fact's
`attributes.duplicates` — the DUPLICATES link S-3 and the backlog AC3
require, V12-conformant, without re-versioning the peer (the
relationship is symmetric in the relationship model; retroactive peer
re-versioning would be churn without correctness gain). `NOT_EQUIVALENT`
links nothing. Both Facts remain ACTIVE. Either merge direction on
containment is conservative: the existing Fact is never rewritten.

### 3.4 Failure recording [N-10]

New closed-set stage **`MERGE_FAILED`** (attempted: the merge judgement
ran), reasons: `EVIDENCE_ALREADY_ATTACHED`, `ACCEPTANCE_REFUSED`,
`CONCURRENT_MERGE` (reserved, unemitted — §3.2 step 11 decision),
`MERGE_NOT_POSSIBLE`. Every refusal lands in the log and the
FailureStore projection; no partial state survives (the structural
closure of §3.2 step 8).

### 3.5 Density correctness after merging

`build_density_report` counts claims from attachments of **ACTIVE**
Facts only: superseded versions' attachments are already counted on
their ACTIVE successors. Counting every version would double-count
corroboration after any merge. For non-merged corpora the numbers are
unchanged.

### 3.6 Import budget

`extraction.py` adds `replace` (stdlib dataclasses), `MergeJustification`
to the EXISTING `oip.fact` import. The oip-import SET stays exactly
`{acceptance, claim, contract, evidence, fact, store}` — 6/6; no new
module; module count stays 37; DAG unchanged.

### 3.7 Boundary evolution with provenance (never silent)

T03.1.1's interim "extraction never merges" boundary is intentionally
superseded by this task. The following are re-semantified WITH
provenance comments, strengthened rather than weakened:
`test_extraction.py` (merge assertions replace two-Fact assertions),
`test_decomposition.py` (merge asserted with justification/version),
`verify_t03_1_1` §E (merge-with-justification checks),
`verify_t03_1_2` §B/C (counts + merge), `verify_t03_1_3` §E,
`probe_t03_1_1` P15 (deliberate-merge probe), `probe_t03_1_3` P17
(replay-refusal probe), `mutate_t03_1_1` M10 (mutant becomes
"merge machinery disabled" — killed by the merge assertions).
T03.1.1's AC text, the backlog, and all ratified decisions remain
byte-identical.

## 4. What is deliberately NOT implemented

- **T03.1.5** claim-type classification (caller-stated).
- **T03.1.6** contradiction detection (`CONTRADICTS` machinery untouched).
- **T03.2.1** acceptance-path anchor verification (store
  `anchor_verifier` stays None).
- No retroactive DUPLICATES re-versioning of peers; no merge across
  different claims (synonyms are NOT_EQUIVALENT — S-3 judgement gap
  stays); no compound-claim splitting (M-19 open); M-20/M-67/M-59 stay
  open; no modification to `claim.py`, `fact.py`, `semantic.py`,
  `store.py`, ratified decisions, or the backlog.
