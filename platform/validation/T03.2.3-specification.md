## 4. Source reconciliation — what is ratified vs. what this specification must decide

**Already ratified (this specification invents none of it):**

1. Two metrics, not one: **hallucination rate** = "proportion of
   audited Facts judged `UNSUPPORTED`"; **drift rate** = "proportion
   judged `DRIFTED`" (S-5 Layer 3 table, verbatim).
2. Both are **platform quality metrics**, **feed N-3's stage-2 proxy
   measures**, are **tracked as trends**, and are **reported alongside
   platform output** (S-5).
3. Layer 3 **consumes audit records produced under F-A1**; Layer 1's
   `anchor_failure_rate` is explicitly NOT the hallucination rate
   (F-A1).
4. The judgement vocabulary is closed: `FAITHFUL | DRIFTED |
   UNSUPPORTED`, no defaults, no coercion (F-A1 R7) — so every judged
   record is in exactly one category.
5. The register dedups to one selection per `(fact, policy_version)`;
   "a superseding policy version may select the same Fact again — that
   is a new audit, not a duplicate" (F-A1 R5/R10, recorded in the
   module).
6. The 5% POLICY_V1 rate is a per-draw configuration constant, NOT a
   per-Fact probability and NOT an estimator (F-A1 R3 + §14
   multi-stratum annotation). **It must never appear as a denominator,
   numerator, or correction factor in the metrics.**
7. N-3 binds this task: "hallucination rate published as a platform
   quality metric."

**Explicitly deferred to this specification (F-A1 takes no position;
ratified records name this document as the resolver):** denominator
semantics for pending records; SelectionFailure treatment;
zero-denominator behavior; policy-version scoping; the publication
mechanism ("published"/"reported alongside platform output" has no
mechanical definition in this codebase); trend time basis,
aggregation, and representation; module placement; the T03.2.3 ↔
T09.1.4 boundary; M-20 closure. These are resolved as owner decisions
OD-1…OD-8 in §6.

### OD-1 — Denominator semantics

**Question:** exactly which `AuditRegister` records form the
denominator of the two rates?

**Options evaluated.**

- **(a) Judged records only** — denominator = records with a recorded
  judgement; numerator = the respective category. *Recommended.*
- (b) All selected records (pending included in denominator).
- (c) Pending counted as non-hallucinated (implicit innocence).
- (d) Pending suppresses the metric entirely (no publication while
  any selection is unjudged).

**Evaluation against the sources.** S-5 defines the metrics over
"**audited** Facts" and the backlog over "**audit results**"; a
pending record is selected but not yet audited — it holds no result
(F-A1 R7: no judgement, no partial judgement, no default). Option (b)
makes the rate a function of audit **latency** rather than extraction
quality — an operational throughput measure masquerading as a fidelity
measure, and biased toward 0 whenever auditors are slow. Option (c)
worsens it: it assumes innocence for unaudited units, exactly the
failure S-5 exists to prevent. Option (d) makes publication hostage to
a continuously growing register — with pending selection at any time,
the metric would never publish. Option (a) is the only reading in
which the denominator is exactly the set of things that have audit
results, matching both S-5's wording and the backlog AC.

**Record-class resolution (A–H of the owner instruction):**

| Class | Numerator | Denominator | Rationale |
|---|---|---|---|
| A. FAITHFUL judged | no | **yes** | An audit result; the closed 3-value set makes categories exhaustive |
| B. DRIFTED judged | drift rate | **yes** | S-5 drift-rate numerator |
| C. UNSUPPORTED judged | halluc. rate | **yes** | S-5 hallucination-rate numerator |
| D. selected-but-pending | no | **no** | Not an audit result (OD-1a); count carried as context so the rate's coverage is honest |
| E. `SelectionFailure` | no | **no** | An N-10 operational failure to *select* — no audit unit, no judgement possible; coupling the quality metric to operational noise corrupts both (N-10 keeps them on separate surfaces); count carried as context |
| F. duplicate-selection attempts | — | — | Structurally impossible to count: `DuplicateSelectionError` is raised and **nothing is appended** (verified); the metric inherits the register's dedup guarantee |
| G. multiple policy versions | per scope | per scope | Each judged record counted exactly once per scope (OD-3) |
| H. lacking a final judgement | no | **no** | Identical to D: the register permits no other judgement-absent state |

**Recommended decision (OD-1):** the denominator is the set of
**judged** records in scope; formulas in §7. Context counts (pending,
selection failures) are published alongside, never inside, the rates.

### OD-2 — Zero-denominator behavior

**Question:** what is the rate when zero judged records exist in
scope?

**Options evaluated.** (a) `0.0`; (b) `None` (unavailable) with
counts still published; (c) a string/"insufficient data" sentinel.

**Evaluation.** `0.0` asserts "no hallucinations observed" when
*nothing was audited* — the exact dishonesty S-5's publication
principle exists to prevent ("publishing the rate is what converts an
unknown risk into a known one"; Article X: state what you do not
know), and the owner instruction prohibits it. A string sentinel is
not composable and breaks the explicit-contract discipline (N-4).
`None` with the counts published is honest (the consumer sees
`judged == 0`), total (defined for every register state), and
deterministic.

**Recommended decision (OD-2):** both rates are **`None` when the
judged count in scope is 0**, and the snapshot still exists and
publishes its counts. The snapshot type must make a float rate with a
zero judged count unrepresentable (constructor validation, the
module's fail-closed dataclass discipline). Layer 1's
`anchor_failure_rate` (0.0 on empty, vacuous mechanical-check
semantics) is a different layer and is **not modified** by T03.2.3.

### OD-3 — Policy-version semantics

**Question:** how do multiple `SamplingPolicy` versions interact with
the metrics?

**Options evaluated.** (a) combined across all versions only;
(b) per-version only; (c) **both** — a global scope and
per-`policy_version` scopes, each an exact count over records;
(d) per-Fact collapsing across versions.

**Evaluation.** The register's own ratified semantics state a
superseding version selecting the same Fact "is a new audit, not a
duplicate" — so global counting of every judged record once is
correct and is *not* double-counting; per-Fact collapsing (d) would
require inventing a rule for which of two judgements represents the
Fact (rejected — no ratified basis). Per-version scoping (b alone) is
the comparison-safe view — a new policy version changes the sampled
population (and, per the §14 multi-stratum annotation, its union
structure), so regimes should not be silently mixed — but S-5's
metric is platform-level, requiring a global view (a alone).

**Double-counting prevention (normative if ratified):**

1. Register dedup: at most one record per `(fact, policy_version)` —
   re-auditing under the same version is structurally impossible.
2. Each metric computation enumerates the register exactly once; it is
   a pure function of register contents (idempotent: recomputation
   yields an equal snapshot).
3. Per-version scopes are disjoint by construction; the global scope
   is their disjoint union (counts add up — a tested consistency
   property).
4. The metrics consume **judgement records only** — never the
   policy's configured rate, never the 5%, never any estimator
   (owner instruction + §14 annotation).

**Recommended decision (OD-3):** option (c). Every snapshot and trend
carries its scope: `None` = global (all judged records), or a specific
`policy_version` (int ≥ 1, bool rejected — the module's discipline).
An empty scope is a valid, honest answer (judged 0 → rates `None`),
not an error.

### OD-4 — Publication surface

**Question:** what does "published as a platform quality metric" and
"reported alongside platform output" mean mechanically in THIS
codebase?

**Grounding.** This platform has no network, no external surface, and
no output-reporting pipeline (N-1 boundary; the no-network rule). The
established in-platform meaning of a published quality measure is the
Layer-1 precedent: a first-class, queryable, deterministic rate on the
surface that owns the measurement (`AnchorVerifier.anchor_failure_rate`
in `semantic.py`). N-3's binding for T03.2.3 is satisfied by a
queryable platform surface; T09.1.4 later wires stage proxies into
phase-exit criteria (M-52), and T03.3.1's P3-exit verification
consumes "hallucination rate published."

**Recommended decision (OD-4):** publication = a **queryable,
deterministic metric surface on the audit module**, consisting of
(*proposed* names, semantics normative):

- **`QualityMetricSnapshot`** — frozen value type carrying: the scope
  (global or `policy_version`), the counts `judged`, `faithful`,
  `drifted`, `unsupported`, `pending`, `selection_failures` (context
  counts per OD-1), and the two rates `hallucination_rate` /
  `drift_rate` (`float | None` per OD-2). Constructor-validated:
  counts consistent (`faithful + drifted + unsupported == judged`),
  rates `None` iff `judged == 0`, rates in `[0.0, 1.0]` otherwise.
- **`quality_metrics(register, policy_version=None) ->
  QualityMetricSnapshot`** — pure module-level function; computes the
  current (cumulative-over-register) snapshot under its lock via
  `snapshot()`. Same register state → equal snapshot, always (N-4).
- **`metric_trend(register, policy_version=None)`** — the trend
  counterpart (OD-5).
- The **`AuditRegister` class itself is unchanged** — no new methods:
  the T03.2.2 register surface (§14 gate 28) stays intact; Layer 3 is
  added *beside* the register as pure functions over it, mirroring how
  the store's hook kept the register outside the store.
- Immutability: snapshots are frozen values; the register remains the
  only mutable (append-only) source; metric computation never mutates
  anything and triggers nothing (non-gating preserved).

**"Reported alongside platform output"** means: the surface is part of
the platform's public audit API and is available to any consumer of
platform output at consumption time. T03.2.3 does **not** attach
metrics to output objects, annotate Intelligence Objects, gate
anything, or build an external channel (all prohibited, §21).

**What T09.1.4/T09.1.2 later consume:** the snapshot and trend
functions and their value types — a stable, importable,
deterministic stage-2 metric surface. **What T03.2.3 must NOT
implement because it belongs to T09.1.2/T09.1.4:** general
observability (stage throughput, failure-rate visibility — T09.1.2's
ACs), the multi-stage proxy framework, phase-exit wiring, persistence,
dashboards, alerting (§13).

### OD-5 — Trend semantics

**Question:** how is "trend trackable over time" realized?

**A. Time basis — `judged_at`** (*recommended*). The metrics are over
audit **results**; a result exists exactly when `judged_at` exists.
`selected_at` would attribute result-time information to selection
time, and pending records (no result) would be unassignable. No other
authoritative timestamp exists on the record (verified field list).

**B. Aggregation — snapshot + sparse daily series** (*recommended*).
Two artifacts: (i) the cumulative snapshot (OD-4); (ii) a time-bucketed
series of per-bucket snapshots. Buckets are **UTC calendar days**
(`judged_at` normalized to UTC; a naive `judged_at` is interpreted as
UTC — a deterministic rule, no environment-dependent local-time
conversion, N-4). Alternatives evaluated and rejected:
cumulative-only (cannot show direction — S-5's stated purpose is
telling "whether extraction is improving or degrading"); rolling
window (an invented parameter with no ratified basis); hourly
(needlessly fine for a 5%-sampled stream); monthly (too coarse).
Bucket granularity is the one free parameter here — it is an owner
decision being ratified, not a silent choice.

**C. Minimum representation** (*proposed* names, semantics normative):
**`MetricTrendPoint`** = frozen `(utc_date: date, snapshot)`; the
trend is an ordered, ascending-by-date tuple of points. Series
computed by the same pure-function discipline as the snapshot.

**D. Ordering and determinism:** the trend is a pure function of the
register: same contents → same series; insertion-order independent; a
record belongs to exactly one bucket; buckets strictly ascending, one
per date.

**E. Empty buckets:** the series is **sparse** — a bucket exists only
for a UTC date with ≥ 1 judged record in scope. Absence means "no
audit results in that period" and is itself the honest representation;
fabricating empty buckets (with which range? at what granularity?) adds
invented parameters and no information. Each bucket's counts carry its
reliability.

**F. Policy-version scoping:** trends are available in both scopes
(global default; per-version per OD-3). A policy-version change starts
a new sampling regime; the per-version trend is the comparison-safe
view. The global trend remains published (S-5's platform-level
metric); its docstring must state that it spans policy regimes.

**No statistical claims** (no confidence intervals, no significance,
no extrapolation, no sample-size caveats beyond the published counts) —
S-5/F-A1 disclaimer discipline.

## 7. Exact formulas (normative — ratified, F-A2)

For a scope `S` — the set of **judged** `AuditRecord`s in the
`AuditRegister`, either global (`policy_version = None`) or
`{r : r.policy_version = v}`:

```
judged(S)                = |S|
faithful(S)              = |{r ∈ S : r.judgement = FAITHFUL}|
drifted(S)               = |{r ∈ S : r.judgement = DRIFTED}|
unsupported(S)           = |{r ∈ S : r.judgement = UNSUPPORTED}|

hallucination_rate(S)    = unsupported(S) / judged(S)   if judged(S) > 0
                           None                        if judged(S) = 0
drift_rate(S)            = drifted(S) / judged(S)      if judged(S) > 0
                           None                        if judged(S) = 0

context (published, never in the rates):
pending(S)               = |{selected, unjudged records in scope}|
selection_failures(S)    = |{SelectionFailure records in scope}|
```

Properties (tested, §18): `faithful + drifted + unsupported ==
judged` (closed 3-value set); `hallucination_rate + drift_rate ≤ 1`;
the complement of their sum is the FAITHFUL proportion (published via
counts, not as a third rate — S-5 names exactly two metrics);
`hallucination_rate, drift_rate ∈ [0.0, 1.0]` or `None`. **The
configured sampling rate (5%, POLICY_V1) never enters any formula.**

Trend bucketing (OD-5):

```
utc_date(t)  = t.date()                              if t.tzinfo is None
               t.astimezone(timezone.utc).date()     otherwise
trend(S)     = ascending series of (d, snapshot(S ∩ {r : utc_date(r.judged_at) = d}))
               for every UTC date d with ≥ 1 judged record in S
```

## 8. Denominator semantics (normative — ratified, F-A2)

The denominator is the judged-record set of the scope (OD-1, §7).
Pending and SelectionFailure records are **context counts only**
(§7); duplicate selections cannot occur in the register (raised, never
appended); no other judgement-absent state exists. The rates are
computable at any time from any register state and are total (OD-2).

## 9. Pending and SelectionFailure semantics (normative — ratified, F-A2)

- **Pending** (selected, unjudged): excluded from numerator and
  denominator; `pending` count published in the snapshot so consumers
  can see how much of the sample awaits judgement (S-5: consumers can
  weigh output appropriately; F-A1 accepted judgement latency as real).
- **SelectionFailure** (N-10): excluded from both; count published as
  operational context. The register already exposes
  `selection_failures()`; the snapshot surfaces the count beside the
  rates so the sample's *selection health* is visible next to its
  *results* — measurement of operational failure stays N-10's concern,
  not a quality-rate component.

## 10. Policy-version semantics (normative — ratified, F-A2)

Both scopes (global + per-version), exact counts, disjoint-union
consistency, and the four double-counting guarantees of OD-3. Scope
argument validation: `None` → global; `int ≥ 1` (bool rejected) →
per-version; anything else → error, fail-closed (module discipline).
An empty scope is a valid answer (judged 0, rates `None`).

## 11. Publication semantics (normative — ratified, F-A2)

The queryable surface of OD-4: `QualityMetricSnapshot` +
`quality_metrics(register, policy_version=None)` + `metric_trend(
register, policy_version=None)` (*proposed* names) — pure, immutable
values, deterministic, register class unchanged, no new imports, no
gating, no object-model contact (CI-1; the snapshot shares no type
with the IOM). "Reported alongside platform output" = available on
the platform's public audit API at consumption time (OD-4 grounding).

## 12. Trend semantics (normative — ratified, F-A2)

`judged_at` time basis; UTC calendar-day buckets (naive timestamps
read as UTC); sparse series (no empty buckets); ascending order;
pure-function determinism; both scopes; counts in every bucket; no
statistical claims (OD-5, §7).
