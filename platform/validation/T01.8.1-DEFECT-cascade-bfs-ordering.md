# DEFECT — Cascade partial-retraction spares an object whose entire support is withdrawn

**Found during:** `T01.8.1` Phase 1 Exit Gate (final run, after `T01.2.4-R1`)
**Module:** `oip/cascade.py`
**Severity:** Correctness — silent knowledge corruption through the grounding layer
**Status:** **RESOLVED** — repair (b), fixpoint iteration. See §6.

---

## 1. Statement

`CascadeInvalidation.cascade()` can leave an object `ACTIVE` after **every one of
its upstream references has been withdrawn** by that same cascade. The object is
misreported as `partially_retracted`.

This is precisely the condition I6 exists to prevent, and the same class of
silent corruption that motivated N-9.

---

## 2. Root cause

`_collect()` (oip/cascade.py:159) performs a **breadth-first traversal**, which
orders dependents by **shortest path from the origin**:

```python
while frontier and depth < self.max_depth:
    depth += 1
    for object_id in frontier:
        for child in sorted(graph.children(object_id)):
            ...
            ordered.append(child)
```

`cascade()` then evaluates eligibility in that order, maintaining a `doomed` set
and relying on this documented assumption (oip/cascade.py:253-257):

> "`ordered` is breadth-first from the origin, so a dependent is always
> considered after its own upstream. [T01.2.4]"

**That assumption is false.** In a DAG, shortest-path order is *not* a
topological order. A node with one upstream at distance 1 and another at
distance 5 is discovered at distance 2 — **before** its distance-5 upstream is
decided. When `_retains_valid_upstream()` runs for that node, the deep upstream
is still `ACTIVE` and absent from `doomed`, so it is counted as "still
attesting". The node is spared as a partial retraction. The deep upstream is
then invalidated moments later, and nothing revisits the spared node.

A topological order (or a fixpoint) is required; BFS order is not sufficient.

---

## 3. Reachability — established through the production API

The property "every DERIVES_FROM edge spans exactly one pipeline stage" would
make BFS order topological and the defect unreachable. That property **does not
hold**, and this was verified mechanically rather than assumed.

Six of the eight derived types enforce a single permitted upstream type
(`problem.py:367`, `pattern.py:356`, `opportunity.py:409`, `solution.py:331`,
`execution.py:342`, `feedback.py:292`), e.g.:

```
ProblemError: a Problem derives from Facts only; ['obj-pr-9'] are not Facts [R-6]
```

**`Validation` imposes no such rule** — and correctly so. IOM §3.7 specifies
only that a Validation

> `DERIVES_FROM` the object containing the tested claim; `TESTS` the specific claim.

and IOM line 169 types `DERIVES_FROM` as **`any → any`**. `oip/validation.py:272`
therefore requires only that `tests_claim.object_id` appear in `derives_from`.
A Validation may legitimately derive from objects at different depths.

Confirmed reachable through the **typed production write path**
`store.write_validation()` — the object passed V1–V12, I1–I8 and V-V1…V-V6:

```
write_validation ACCEPTED a Validation with upstreams at stages 1 and 5
  BFS plan: ['F', 'F2', 'PR', 'VA', 'PT', 'OP', 'SO']
                            ^^^^ VA decided before its upstream SO

  E   RETRACTED      F   INVALIDATED     PR  INVALIDATED
  PT  INVALIDATED    OP  INVALIDATED     SO  INVALIDATED
  F2  INVALIDATED    VA  ACTIVE   <-- every upstream withdrawn

  I6 violations after cascade : 1
```

Reproducers:
- `validation/probe_t01_8_1_final.py` — probes P1, P2 (uneven-depth diamonds)
- `validation/probe_t01_8_1_legal_skew.py` — legal objects, generic write path
- `validation/probe_t01_8_1_production_api.py` — **typed `write_validation()` path**

---

## 4. Why the existing suite missed it

- All 5 tests in `tests/test_partial_retraction.py` use **uniform-depth**
  lineage, where BFS order coincides with topological order.
- No test anywhere constructs a lineage edge spanning more than one stage
  (`grep -rln "ObjectType.VALIDATION, \[" tests/` → no matches).
- The gate verifiers pass (`exit_gate_t01_8_1_rerun.py` **91/91**,
  `exit_gate_t01_8_1_tasks.py` **26/26**) because they assert the *presence and
  shape* of the partial-retraction rule, never its behaviour under a
  non-uniform graph.

The `IntegrityVerifier` **does** detect the resulting state (1 × I6 violation),
so the corruption is detectable after the fact — but the detective control
fires only if someone runs an audit; the preventive control failed.

---

## 5. What is NOT being decided here

No fix has been applied. Two candidate repairs exist and the choice between
them is **not mine to make**:

- **(a)** replace BFS ordering with a topological order over the induced
  subgraph; or
- **(b)** iterate the eligibility pass to a fixpoint.

Both alter cascade's traversal — the mechanism N-9 constrains ("mechanical
integrity operation… idempotent, terminating"). Either is defensible under N-9,
which specifies cascade's *properties* but not its traversal order. Selecting
one is an implementation decision within a frozen architecture, and the
ordering guarantee is currently asserted only in a source comment, not in any
ratified document.

**Specification gap surfaced:** no ratified source states the order in which
cascade must evaluate dependents, yet the partial-retraction rule (N-9,
IOM §3.2) is order-sensitive. Failing closed and reporting rather than choosing.


---

## 6. Resolution — repair (b), fixpoint iteration

**Selected repair: (b) iterate eligibility to a fixpoint.** Repair (a),
topological ordering, was rejected because `plan()`'s breadth-first ordering is
an existing, documented, *tested* public contract
(`test_plan_is_breadth_first_then_lexicographic`, and `result.invalidated ==
planned`). Repair (a) would have forced those tests to be rewritten, i.e.
weakened, to accommodate the fix. Repair (b) leaves `_collect()` and `plan()`
byte-identical and changes only how eligibility is *decided*.

### Change (the only production change)

`oip/cascade.py`, inside `cascade()`. The single eligibility pass is split:

1. Order-independent classification (unresolvable / already-terminal /
   illegal-transition) is decided once, in traversal order, exactly as before.
2. Remaining candidates are resolved to a **fixpoint**: repeatedly condemn any
   candidate that retains no valid upstream, until a full pass condemns nothing
   new.
3. Results are emitted in the original traversal order, so `plan()`'s reported
   sequence and `result.invalidated == planned` are preserved.

Correctness no longer depends on any ordering property of `_collect()`.

**Termination:** every pass except the last adds at least one object to
`doomed`; `doomed` is bounded by the finite dependent set. The guard
`if object_id in doomed_dependents: continue` is load-bearing for termination,
not an optimisation — removing it makes the loop re-condemn settled objects and
signal progress forever (observed empirically).

No architecture, contract, API, ownership, acceptance rule or specification was
modified. `oip/integrity.py` is unchanged (md5 `42f1a950…` before and after).

### M19 survivor — equivalent mutant, not a test gap

M19 swaps `object_id in doomed_dependents` for `object_id in doomed`. `doomed`
differs from `doomed_dependents` only by `origin_id`, and the loop iterates
solely over `undecided`, which is built from `ordered` — and `_collect()` seeds
`seen = {origin_id}` and appends only unseen children, so the origin can never
appear there. The two predicates are therefore identical on this domain.
Verified structurally and empirically (origin appeared in `ordered` in 0 of 5
graph shapes).
