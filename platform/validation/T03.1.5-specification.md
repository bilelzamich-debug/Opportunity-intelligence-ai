## 3. The classification surface, as it exists (verified, not recalled)

The task does not require new mechanism; it requires that the ratified F-V4
surface exist end-to-end and be provable. It exists in **five layers**:

| # | Layer | Where | Enforcement |
|---|---|---|---|
| L1 | Request | `ExtractionRequest.__post_init__` (`oip/extraction.py`) | `claim_type` must be a `ClaimType` member; `ATTRIBUTED_OPINION` without non-blank `attributed_to` raises at construction — the producing path's only door |
| L2 | Claim projection | `ExtractionRequest.as_claim` / `decompose` (`oip/extraction.py`) | the same check re-runs on the projection; the classification travels with the claim text |
| L3 | Fact construction | `Fact.__post_init__` (`oip/fact.py`) | `claim_type: ClaimType` is a field with **no default** — the classification must be stated; the **pairing** clause (opinion ⇒ non-blank `attributed_to`) raises `ClaimTypeError` here. Enum membership itself is NOT re-checked at L3 — see Finding 1 |
| L4 | Acceptance | `fv4_claim_type_declared` (`oip/fact.py`, wired in `FACT_RULES`) | V-rule re-check at the store boundary on every `write_fact`: unknown `claim_type` FAILs; opinion without attribution FAILs; no payload SKIPs (never a guessed PASS) |
| L5 | Versioning | `Fact.with_attachment` (`oip/fact.py`) | merges re-version via `dataclasses.replace` — `claim_type` and `attributed_to` are preserved across every merge (T03.1.4), so classification cannot be laundered by corroboration |

Store round-trip: `write_fact` re-registers the payload with
`claim_type=fact.claim_type` and `attributed_to=fact.attributed_to`
(`oip/store.py`), and `get_fact` returns the registered payload — the
classification survives persistence.

**Boundary, stated not invented.** `ATTRIBUTED_OPINION ⇒ attributed_to` is
F-V4. The converse (an `ASSERTION` carrying `attributed_to`) is not a
ratified constraint; the extraction layer therefore does not copy the
optional attribute unless the type requires it (`extraction.py`,
attributed_to ternary), while the verbatim claim and qualifying context
still carry whatever the source text contained. No refusal is fabricated
for a legal input; no field is defaulted. Recorded here because
T03.1.1 chose the behavior; nothing in this task changes it.

**What classification is in this architecture.** `claim_type` is supplied by
the extractor and ENFORCED by the platform — never inferred by it. Any
platform-side "classifier" would be a semantic judgement N-4 and S-3 exclude.
The deliverable "Claim type classification" is thus: a closed two-member
enum, mandatory at every construction and acceptance layer, with attribution
demanded exactly where the model demands it.

## 4. Closure determination

**`T03.1.5` CLOSES on existing evidence** (T02.1.3 precedent), demonstrated
mechanically by `validation/verify_t03_1_5.py`:

- AC1 — L1–L5 above: enum closedness, required-field proof, request→Fact
  population for BOTH members, round-trip through `get_fact`, preservation
  across a T03.1.4 merge re-version.
- AC2 — refusal of `ATTRIBUTED_OPINION` with missing/blank/whitespace
  `attributed_to` at L1, L3 and L4; acceptance of the compliant case; the
  rule's SKIP semantics when the payload is absent (no guessed PASS).
- Adversarial: bypass attempts (raw string "ASSERTION", `None`, non-enum,
  `replace()`-based laundering of attribution, direct `write_fact` of a
  constructed bad Fact) — every bypass meets a refusal, none leaks a Fact.

No production file changes. Frozen modules stay byte-identical. Test corpus
unchanged (the behaviors are already covered by `test_fact.py`,
`test_extraction.py`, `test_decomposition.py`); the verifier proves it from
the code, not from recollection.

## 5. Findings from adversarial verification (documented, not patched)

`verify_t03_1_5.py` ran against the live corpus; two observations are
recorded because the protocol requires surfacing what the specification
did not anticipate — neither is fixed here, and neither blocks the ACs.

**Finding 1 — membership layering.** Enum membership of
`Fact.claim_type` is enforced at L1 (request) and L4 (acceptance), not at
L3 (constructor): a hand-built Fact with `claim_type=None` transiently
exists, then FAILS `fv4_claim_type_declared` at `write_fact` and can never
be persisted. This matches N-08 — the acceptance path is the authority —
and the production pipeline cannot produce such a Fact (V7 confines
creation to `extract()`, which passes L1). A constructor-side membership
check would be pure defense-in-depth on a path only tests traverse;
`fact.py` is a frozen P1 module, so any change requires the annotation
route, not an implementation choice. **Surfaced to the Project Owner as a
P5-class hardening candidate.**

**Finding 2 — classification is canonical-level, not utterance-level.**
An `ATTRIBUTED_OPINION` extraction judged EQUIVALENT to an existing
`ASSERTION` canonical **merges and keeps the canonical's classification**
(S-3's four conditions are subject, predicate, qualifier, value —
`claim_type` is not a condition; D-05 makes the Fact the canonical claim,
not the extraction event). Demonstrated mechanically in verifier section
I. Consequence: a Fact's classification is the classification of its
FIRST persisting extraction; later dissenting classifications attach
without altering it. This follows the ratified corpus exactly, but it
touches IOM §3.2's failure case "opinion recorded as assertion": the
platform does not adjudicate type conflicts at merge time. If the Owner
wants classification disagreement to refuse or annotate merges, that is a
decision record (it changes S-3 or T03.1.4 policy), not a code edit.
