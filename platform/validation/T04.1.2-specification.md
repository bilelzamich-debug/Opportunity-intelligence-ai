## 3. What exists and is preserved unmodified

P-V2 (lexical rejection at acceptance, every write, absence + remedy markers,
word-bounded) and P-I1 (continuous integrity re-check of **every** version,
reporting) are complete since T01.7.3 and are **not moved, duplicated, or
weakened**. T04.1.1's engine already routes v1 inferences through P-V2. What
does not exist — the gap T04.1.2 closes — is any engine path that can produce
a **new version** of a Problem (the IOM's reformulation trigger) and any
write-time enforcement of solution-independence over a version **chain**.

## 5. Versioned mode (predecessor_id supplied)

Ordered, fail-closed. Steps 1–8 leave **no state change** on refusal.

1. **Resolve the predecessor** — `store.find(predecessor_id)`.
   Missing → `PREDECESSOR_NOT_FOUND` (not-attempted).
2. **Type** — must be `ObjectType.PROBLEM` (N-14/V7: Problem Intelligence
   modifies Problems only). Otherwise → `PREDECESSOR_NOT_A_PROBLEM`.
3. **Lifecycle** — must be `ACTIVE` (the IOM transition is
   `ACTIVE → SUPERSEDED`; a non-ACTIVE predecessor has no legal path).
   Otherwise → `PREDECESSOR_NOT_ACTIVE` (reason token names the status).
4. **Chain solution-independence over EXISTING versions** —
   `lineage = store.resolve_lineage(...)`; every version from
   `store.versions_of(lineage)` (public API); the statement of each
   registered payload is evaluated with the **authoritative
   `detect_solution_language`** — the P-V2 machinery, not a second lexical
   definition. The chain never becomes acceptable merely because its newest
   version is clean: if ANY existing version trips the detector, the
   inference refuses with `CHAIN_NOT_SOLUTION_INDEPENDENT` (attempted),
   naming every violating version and marker. The PROPOSED successor's
   statement is not part of this pass — it is held to the same standard by
   the authoritative dry-run (step 7): a smuggling successor is refused
   with `STORE_REJECTED` (P-V2) before any state changes. A version whose
   payload cannot be read refuses fail-closed (`STORE_REJECTED` /
   `REGISTRY_GAP`): a chain that cannot be fully read cannot be certified
   solution-independent.
5. **Standalone gates** — the full T04.1.1 path runs unchanged (request
   validity, Fact resolution, ACTIVE eligibility, Evidence resolution, N-16
   derivation, S-4 floor, temporal consistency, confidence composition).
6. **Compose the successor** — identity via `store.allocator.succeed(
   predecessor.attributes.identity)` (V11: version = predecessor + 1,
   lineage_id constant); `derives_from`/`supporting_facts` from the request
   (the widened or re-stated support set); all other construction identical
   to the standalone path.
7. **Authoritative dry-run before any state change** — the composed
   successor is evaluated against the public `PROBLEM_RULES` tuple
   (P-V1..P-V6, the authoritative implementations) over a minimal
   `AcceptanceContext` carrying exactly the fields those rules consult —
   `attributes`, the Problem payload (`problem`), and a `fact_claim_text`
   provider built on public store reads (`get_fact`), as P-V6 does at
   acceptance. Any FAIL →
   `STORE_REJECTED` refusal **before** the predecessor is touched. This is
   the structural closure of the versioned-write failure surface (§7).
8. **Versioned write** (the extraction merge recipe, exactly):
   `store.transition(predecessor_id, SUPERSEDED, reason)` →
   `store.write_problem(successor, predecessor_id=predecessor_id)`.
   Success: predecessor SUPERSEDED, successor ACTIVE (acceptance is the
   PROPOSED→ACTIVE transition), V11/I5 hold, `P-I1` integrity intact.
9. **Outcome** — re-fetch the registered payload; return it with
   `predecessor_id` set.

## 6. Cross-version solution-independence semantics

- Evaluated over **`problem_statement` only** (IOM P-V2 scope). Severity,
  frequency, domain, population, workarounds, confidence and all other
  fields are out of scope — no new independence semantics are invented for
  them.
- The detector is `detect_solution_language` with its default
  `SOLUTION_MARKERS` — the same set P-V2 uses at acceptance. No second
  definition exists in this module.
- P-V2 at acceptance and P-I1 in continuous integrity remain authoritative;
  the engine check is a precondition that makes P-I1 **enforced at the
  versioned-write boundary** on the engine path, never a bypass and never a
  replacement for the integrity check.
- Marker-set evolution (legal tuning per problem.py: "the marker set may be
  extended without a decision record provided P-V2's meaning is unchanged")
  is exactly the case the chain check catches: a version written clean under
  an older marker set and now tripping a marker blocks further versioned
  inference of that lineage until the violation is resolved through
  integrity-governed channels.

## 7. Failure semantics on the versioned path (the precedent, precisely)

`oip/lifecycle.py` (R-2) gives `SUPERSEDED` **no outgoing transitions**, and
the extraction merge path — the established versioned-write precedent —
therefore does **not** restore a predecessor after a failed successor write:
restoration is structurally impossible without an illegal transition. The
precedent closes the failure surface instead:

- every acceptance rule that could reject the successor is pre-satisfied
  **before** the predecessor is transitioned (here: the engine gates +
  the authoritative `PROBLEM_RULES` dry-run of §5.7; the universal rules
  V1–V12 are closed by construction exactly as the extraction merge argues:
  V1/V9 by construction, V2/V3/V12 by resolved Facts, V4 by Fact lineage,
  V5 by the derived ceiling, V6 by the explanation, V7 by the engine, V8 by
  the pre-check, V10 by upstream-only references, V11 by `succeed()`);
- should a write still fail, the refusal is recorded
  (`STORE_REJECTED`/`WRITE_FAILED_AFTER_TRANSITION`) and **names the exact
  surviving state**: predecessor SUPERSEDED with every attribute and its
  registered payload intact, no successor, the store's acceptance failure
  retained — data intact, fully auditable, nothing silent [N-10].

Known repo inconsistency, reported not fixed: `extraction.py`'s module
docstring (line 139) says the canonical "is restored to ACTIVE if the
successor write fails", contradicting both the R-2 lifecycle table and the
merge code's own except-branch comment ("SUPERSEDED is TERMINAL [R-2], so
the canonical cannot be restored"). `extraction.py` is protected; the stale
docstring line is out of T04.1.2 scope and left byte-identical. T04.1.2
follows the **code** precedent and the ratified R-2 table.

## 8. Refusal stages (N-10, closed set extension)

| Stage | Meaning | `attempted` |
|---|---|---|
| `PREDECESSOR_NOT_FOUND` | predecessor does not resolve | No |
| `PREDECESSOR_NOT_A_PROBLEM` | predecessor is not a Problem | No |
| `PREDECESSOR_NOT_ACTIVE` | predecessor not ACTIVE (reason token = status) | No |
| `CHAIN_NOT_SOLUTION_INDEPENDENT` | any EXISTING version of the lineage trips the authoritative detector (the proposed statement is the dry-run's, step 7) | **Yes** |

All existing stages, their attempted-classification, the log, and the
FailureStore projection are unchanged. `WRITE_FAILED_AFTER_TRANSITION`
reuses `STORE_REJECTED` with a distinct reason token (§7).

- No new graph relationships, no new lifecycle paths, no restore-by-illegal-
  transition, no second lexical detector, no LLM/network/external APIs, no
  observability. Module count stays **39** (no new module; no pin changes).
