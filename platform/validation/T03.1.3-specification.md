## 3. The design (what is built, and why this shape)

### 3.1 The constraint triangle

1. IOM wants `positional_anchor` to be a *precise location*.
2. T03.1.1's pinned tests require `attachment.positional_anchor` to equal the
   **verbatim span** (`test_anchor_preserved_on_attachment`,
   `test_attachment_resolves_and_anchor_locates`) and its verifier pins
   `content.count(anchor) == 1` — and T03.1.1 tests must remain **unchanged
   and passing**.
3. The Fact/Evidence model must not be redesigned (attachment is a frozen
   frozen dataclass; no new fields).

**Resolution:** the attachment's anchor stays the verbatim span
(T03.1.1 behavior preserved byte-for-byte), and T03.1.3 adds the
**positional anchoring layer** beside it:

- every accepted extraction *computes* the positional locator of its span,
- *verifies* it by an O(1) round-trip (fail-closed),
- *records* it in a `PositionalAnchorRegister` — a side register in the
  established N-10/N-22 pattern (registers live outside the object model and
  never enter the lineage graph),
- so every accepted anchor is resolvable **two ways**: verbatim (exact
  substring, T03.1.1) and positional (`chars s-e`, O(1) direct slice —
  T03.1.3, no re-reading).

This is an *additive* capability: no object model change, no behavior change
for any T03.1.1 input, new refusals only where anchoring cannot be
guaranteed.

### 3.2 The locator format (closed)

```
chars <start>-<end>      e.g.  chars 41-78
```

- 0-based, **half-open** (`content[start:end] == span`, Python slice
  convention), units are **code points** (language-agnostic: CJK, RTL and
  astral-plane characters each count as one).
- Resolvable by a **direct slice** — no scan, no re-reading. This is the
  precision the AC demands: `resolve_locator` performs no searching at all
  (mechanically asserted by the verifier via source inspection).
- Parse is strict: full-match `chars [0-9]+-[0-9]+` only — ASCII digits only
  (Python `int()` accepts non-ASCII decimal digits such as `٤٥`; the
  `[0-9]` class rejects them), bounds-checked, `start < end` (a span is
  non-empty by request validation). Anything else is refused, never guessed.

### 3.3 The asymmetry that satisfies AC2 (stated deliberately)

`locate()` uses one `str.find` **once, at anchoring time** — that is the
anchoring *computation*, performed on content already in hand at extraction.
Every *later* location — verification, audit, F-V6/T03.2.1 — resolves via the
recorded locator by direct slice in O(1), with no scan of the Evidence. The
AC governs locating the claim afterwards, not the one-time computation.

### 3.4 Extraction integration (fail-closed, N-10)

`extract()` gains an optional `anchors: PositionalAnchorRegister | None`
keyword. For **every** accepted extraction, unconditionally:

1. compute the locator from the (already unique) span,
2. round-trip `resolve_locator(content, locator) == span`,
3. record `(evidence_ref, span) → locator` when a register is attached.

A round-trip failure — unreachable by construction, which is exactly why it
must fail closed — refuses with a recorded
`ANCHOR_NOT_RESOLVABLE` failure (new closed-set stage, `attempted=True`:
the judgement ran against content in hand). No Fact is created. No anchor is
ever invented or guessed: ambiguity and absence were already refused by the
T03.1.1 gates, and now non-round-tripping locators are refused too.

`ExtractionOutcome` carries `locator` for observability.

### 3.5 The S-5 machinery wiring (existing abstractions only)

- `evidence_span_provider(content)` returns a `SpanProvider` (the T01.4.6
  protocol) that resolves **both** formats: `chars s-e` locators by direct
  slice (any parse/bounds failure → `None`, the protocol's "unresolvable"),
  verbatim-span anchors by exact unique-substring check.
- `fact_anchor_claims(fact)` projects a Fact's attachments + claim into
  `AnchorClaim`s for the `AnchorVerifier`'s `claims_of` (subject and
  predicate; the value is checked at extraction time against the verbatim
  `value_text`, which the Fact itself does not carry — the projection emits
  no value rather than an unfaithful one).
- **Demonstrated, not installed:** F-V6 at acceptance for 100% of Facts is
  `T03.2.1`'s deliverable. The store's default `anchor_verifier` stays
  `None`; the verifier/tests demonstrate F-V6 PASSING mechanically through
  the new provider. No acceptance-path behavior changes.

### 3.6 The register

`PositionalAnchorRegister`: thread-safe, append-only, keyed
`(evidence_ref, span)` → locator. Lookup `locator_for()` is O(1) against the
key — resolving an attachment's anchor to its exact position requires
neither content nor scanning. Conflicting re-registration (same key, same
evidence-independent locator — which is determined by the content, so a
mismatch is a programming error or content drift) raises. Nothing here ever
enters the lineage graph.

## 4. What is deliberately NOT implemented

- **T03.1.2** claim decomposition; **T03.1.4** merging (attachments added by
  merges will record their own locators when that task lands);
  **T03.1.5** classification — untouched.
- **T03.2.1** acceptance-path anchor verification for 100% of Facts (the
  provider and claims projection are delivered and demonstrated; installing
  them store-wide is that task).
- **T03.2.2 / T03.2.3** sampled audit and published rates.
- No marker closure: **M-19, M-20, M-67 all remain open**; F-V6's semantic
  limit (no paraphrase-drift detection) is unchanged.
- No change to any frozen module (`fact.py`, `evidence.py`, `semantic.py`,
  `store.py`), no change to any T03.1.1 test, no change to extraction
  behavior for any existing input.
