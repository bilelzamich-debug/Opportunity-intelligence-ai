## 5. Architectural constraints

1. **C1 — Detection separate from policy.** The layer reports; it never decides. No retry/skip/halt/compensate (M-36).
2. **C2 — Never masked.** A failure must never be reportable as completion, and must survive a bounded stop (the defect fixed at T01.6.1).
3. **C3 — Never silently halts.** The cycle continues past a failure (N-17, AC2).
4. **C4 — FAILED ≠ EMPTY**, "mandatory at every stage" (N-10, AC1).
5. **C5 — Outside the object model**, never in lineage (N-10, Art. V).
6. **C6 — Attributable** to engine, invocation, inputs, configuration, time and nature (N-10's six).
7. **C7 — Orchestration owns no storage**; stores are supplied (v2 §4.12).
8. **C8 — Append-only**, immutable (N-7/N-10 rationale).
9. **C9 — Failure surface ≠ processing surface** (B-12).
10. **C10 — Thread-safe** (N-11).
11. **C11 — No observability vocabulary** — no metrics/alerts/thresholds (M-57 open).

## 6. Defect found during extraction — N-10 conformance gap

N-10 mandates six identifications per failure record. `FailureRecord` (T01.1.7) structurally carries five fields, of which only three of the six are present:

| N-10 requires | Present today | Status |
|---|---|---|
| the engine | — | **ABSENT** (smuggled into `object_id` as the string `"engine:FactExtraction"`) |
| the invocation | — | **ABSENT** (no cycle or invocation identifier) |
| the inputs attempted | — | **ABSENT** (verified: inputs `ev-1`, `ev-2` are unrecoverable from the stored record) |
| the configuration in force | `engine_configuration_ref` | present |
| the time | `recorded_at` | present |
| the nature of the failure | `failed_rules` | present |

Empirically confirmed against a live orchestrated failure. This is a **genuine defect in N-10 conformance**, and it lands exactly on this task: T01.6.3 is the task N-10 binds to make failures *visible*, and a failure whose engine, invocation and attempted inputs cannot be recovered is not surfaced in the sense N-10 requires. `T01.1.7`'s own criterion "Failures attributable to engine and invocation" is likewise unmet.

**Scope decision.** Fixing this is *in scope* because it is a defect on this task's own acceptance path, not a redesign. It will be fixed **additively**: new optional attribution fields defaulting to `None`, so all four existing producers (`acceptance`, `cascade`, `integrity`, `orchestration`) and every existing construction keep working unchanged. Orchestration — the only producer that *has* engine/invocation/input context — will populate them. The other three are not orchestration invocations and legitimately have no invocation identity; they are left as they are rather than inventing one.

## 7. Document conflict — M-36 (must be recorded, not silently resolved)

**The conflict.** `decisions/N-10-failure-representation.md` header states `**Closes** | M-36`, and `decisions/TIMELINE.md` repeats "closes … M-36". But `PKP_v2_Master_Reference.md` §13 still lists M-36 as an open Orchestration item ("Failure-handling policy"), and `marker-crosswalk.md` line 46 confirms canonical **v2 M-36 = "Failure-handling policy"**, distinguishing it from IOM MISSING-36 (outcome intake → M-47).

**Resolution.** The crosswalk (line 56) records that IOM `MISSING-17` "Failure representation" was mapped to **M-36** and annotates the correction: *"(policy + representation)"*. M-36 is therefore a **compound marker** covering two things:

- **failure *representation*** — closed by N-10 (a mechanism now exists to signal failure);
- **failure-handling *policy*** — retry / skip / halt / compensate — which N-10 nowhere specifies. N-10's Decision section defines recording and distinguishability only.

N-10 closes the representation half. **No ratified source anywhere states a retry, skip, halt or compensation policy.** Under Article XI precedence, decision records outrank PKP v2; but a decision record cannot close by assertion a question whose substance it never addresses. Reading M-36's policy half as closed would license inventing retry behaviour from nothing.

**Therefore: the policy half of M-36 is treated as OPEN and failed closed.** This matches T01.6.1 and T01.6.2 precedent. No retry, skip, halt or compensation is implemented. This is recorded as an ambiguity, not resolved.

## 9. Implementation plan

Smallest architecture-compliant change. All additive.

**Step 1 — `oip/acceptance.py`: N-10 attribution fields (defect fix).**
Add to `FailureRecord`, all optional, defaulting to `None`/`()`:
`engine`, `cycle_id`, `invocation_index`, `input_ids`. Add a `satisfies_n10_attribution` property reporting whether all six N-10 identifications are present. No existing field changes; no existing call site breaks.

**Step 2 — `oip/orchestration.py`: populate attribution.**
`_failure_record()` gains the engine, cycle id, ordinal and attempted inputs it already holds and currently discards.

**Step 3 — `oip/orchestration.py`: the surfacing layer (`FailureSurface`).**
A read-only *view* over failures already recorded — it stores nothing of its own, owns no policy, and is constructed from cycle records:
- `failed_invocations()`, `empty_invocations()` — AC1, kept strictly distinct;
- `is_masked_as_completion()` — the never-masked invariant, asserted mechanically;
- `assert_not_masked()` — fails closed if a failure is ever invisible;
- `halted_cycles()` / `continued_past_failure()` — AC2 evidence;
- `unattributed_failures()` — surfaces N-10 attribution gaps rather than hiding them;
- `consecutive_failures()` — a reported fact, no threshold, no action.

**Step 4 — `FailureStore` query surface** (`configuration.py`): add `for_engine`, `for_cycle`, `unattributed` — reads only, matching N-10's "Orchestration reads failure records".

**Explicitly NOT built:** retry/skip/halt/compensate (M-36); metrics, rates, alerts, dashboards, thresholds (M-57 → T09.1.2); severity grading (no vocabulary); the N-11 concurrency boundary (T01.6.4); sequencing (T01.6.5); retention/eviction (unspecified).
